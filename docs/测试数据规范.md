# 测试数据规范（Club Flow）

> 本文档是**测试数据编写规范**：面向负责为本项目各数据表编写测试数据的 agent。
> 目标：编出的数据「能执行、不冲突、讲得通、像真的」——插入后应用可正常启动运行，
> 所有唯一约束/外键语义/状态机校验全部满足，且业务上自洽（余额对得上、人数数得清、时间线不穿越）。

---

## 0. 项目背景速览

社团全流程管理系统：高校社团从申请创建 → 审批成立 → 纳新/活动/经费/互动 → 注销的全生命周期。
技术栈：Spring Boot 3.5 + MyBatis-Plus + MySQL 8（Flyway 管理 schema）+ Redis。

- **Schema 权威来源**：`backend/src/main/resources/db/migration/V1__baseline.sql`（22 张表 + 种子数据）与 `V2__indexes_and_check.sql`（索引 + CHECK 约束）。
- **代码枚举权威来源**：`backend/src/main/java/com/club/enums/` 下 8 个枚举类。
- 所有表字段名以 DDL 为准，本文档只列「编写数据时必须关注的字段」，未列字段按 DDL 默认值处理。

## 1. 全局铁律（违反任何一条 = 不合格）

### 铁律 1：枚举值必须与代码逐字一致
任何 `VARCHAR` 状态/类型字段，取值只能是下表列出的值（大小写敏感，全大写）：

| 字段/场景 | 合法取值 |
|---|---|
| club.status | `PENDING` / `APPROVED` / `SUSPENDED` / `DISSOLVED` / `REJECTED` |
| club_member.member_role | `PRESIDENT` / `VICE` / `MEMBER` |
| club_member.status | `PENDING` / `ACTIVE` / `QUIT` / `REMOVED` |
| recruit.status | `NOT_STARTED` / `IN_PROGRESS` / `ENDED` / `CANCELLED` |
| recruit_record.status | `PENDING` / `PASSED` / `FAILED` / `CANCELLED` |
| activity.status | `DRAFT` / `PENDING` / `PUBLISHED` / `ONGOING` / `ENDED` / `CANCELLED` |
| activity_signup.status | `SIGNED` / `CANCELLED` |
| fund.type / fund_record.type | `INCOME` / `EXPENSE` |
| fund.status | `PENDING` / `APPROVED` / `REJECTED` |
| comment.biz_type | `POST`（代码已实现计数联动）/ `NOTICE` / `ACTIVITY`（DDL 允许，代码暂未联动） |
| user_like.biz_type | `POST`（点赞动态，联动 post.like_count）/ `COMMENT`（点赞评论，联动 comment.like_count） |
| 通用启停状态（sys_user/sys_role/sys_menu/dict_type/dict_data） | `0`（正常）/ `1`（停用） |
| 布尔标记（notice.top、activity.checkin_enabled、dict_data.is_default、sys_config.config_type） | `Y` / `N` |
| sys_user.user_type | `STUDENT` / `ADMIN` |
| sys_role.data_scope | `1` 全部 / `2` 本社团及以下 / `3` 本社团 / `4` 仅本人 / `5` 自定义 |
| club.category | `ACADEMIC` / `CULTURE` / `SPORTS` / `VOLUNTEER`（与 dict_data 字典一致） |
| activity_checkin.status | `1`（已签到，DDL 固定值） |

### 铁律 2：外键引用必须真实存在（先父后子）
数据文件按依赖顺序编写：`sys_user` → `club` → `club_member` → `recruit`/`activity` → `recruit_record`/`activity_signup`/`activity_checkin` → `post`/`comment`/`user_like` → `fund` → `fund_record`。
任何 `xxx_user_id`/`club_id`/`recruit_id` 等引用字段，必须指向**本文件中已插入（或种子数据中已存在）**的记录 ID。

### 铁律 3：时间线自洽
- 结束时间必须晚于开始时间（`end_time > start_time`）。
- 审批时间晚于申请时间；签到时间在活动 `start_time ~ end_time` 窗口内；报名时间在纳新/活动时间窗口内。
- 动态/评论/公告的 `create_time` 建议集中在合理区间（如最近 90 天），避免"2020 年的动态挂在 2026 年的活动上"。
- 种子数据中 `NOW()` 已存在的记录，其后续数据的时间必须晚于种子时间。

### 铁律 4：状态必须合法（状态机校验）
- club：`PENDING → APPROVED/REJECTED`；`APPROVED ⇄ SUSPENDED`；`APPROVED/SUSPENDED → DISSOLVED`；终态 `DISSOLVED/REJECTED` 后无任何子数据。
- activity：`DRAFT → PENDING → PUBLISHED → ONGOING → ENDED`；任意非终态可 `CANCELLED`。
- recruit：`NOT_STARTED → IN_PROGRESS → ENDED`；任意非终态可 `CANCELLED`。
- **非法状态不允许出现在数据里**（例如不能有 `DISSOLVED` 社团的活动还在 `ONGOING`）。

### 铁律 5：数值自洽
- `club.member_count` == 该社团 `club_member.status='ACTIVE'` 的记录数（精确相等，逐条核对）。
- `club.president_id` 必须是该社团 `club_member` 中 `member_role='PRESIDENT'` 的用户 ID，且每个社团**恰好一个**社长。
- `recruit.applied_count` == 该纳新 `recruit_record.status IN ('PENDING','PASSED')` 的记录数，且 `applied_count <= quota`。
- `activity.applied_count` == 该活动 `activity_signup.status='SIGNED'` 的记录数，且 `<= quota`。
- `post.like_count`/`comment_count` == `user_like`/`comment` 中对应的有效记录数（点赞 POST 的进 `post.like_count`，点赞 COMMENT 的进 `comment.like_count`）。
- `fund_record.balance_after` == 该社团**从创建以来**全部 `fund_record` 按时间顺序累加后的余额（收入加、支出减）。
- `fund.amount` 必须 **> 0**（数据库有 CHECK 约束，写 0 或负数直接执行失败）。
- `club.star_level` 取值 0~5。

### 铁律 6：唯一约束不冲突
以下唯一键（来自 V1/V2 DDL），同表数据中不得出现重复值：

| 表 | 唯一键 |
|---|---|
| sys_user | `uk_username(username)` |
| dict_type | `uk_dict_type(dict_type)` |
| club | `uk_club_name(name)`、`uk_club_code(code)` |
| club_member | `uk_club_user(club_id, user_id)` |
| recruit_record | `uk_recruit_user(recruit_id, user_id)` |
| activity_signup | `uk_activity_user(activity_id, user_id)` |
| activity_checkin | `uk_activity_checkin_user(activity_id, user_id)` |
| user_like | `uk_like(biz_type, biz_id, user_id)` |

### 铁律 7：基础字段规范
- 所有 `deleted = 0`（逻辑删除字段，数据必须全部"未删除"）。
- 所有 `sys_user.password` 使用**同一个固定 BCrypt 密文**（对应明文 `admin123`）：
  `$2a$10$7JB720yubVSZvUI0rEqK/.VqGOZTH.ulu33dHOiBE8ByOhJIrdAu2`
  禁止自编密文——否则这些测试账号无法登录。
- 雪花 ID 用**分段固定 ID**（见下），不使用 `NOW()` 作为值。
- `create_time`/`update_time` 写固定字面量（如 `'2026-08-01 10:00:00'`），不要依赖 `NOW()`——保证文件可重复审阅、时间线可控。

### 铁律 8：ID 分段约定（保证可读性与引用一致性）

| 表 | ID 段 | 示例 |
|---|---|---|
| sys_user | 1001 ~ 1999 | 学生 1001~1015、社长 1016~1020、管理员 1（种子保留） |
| club | 2001 ~ 2099 | 社团 2001~2010 |
| club_member | 3001 ~ 3999 | 成员记录 3001 起 |
| recruit | 4001 ~ 4099 | 纳新 4001 起 |
| recruit_record | 5001 ~ 5999 | 报名记录 5001 起 |
| activity | 6001 ~ 6099 | 活动 6001 起 |
| activity_signup | 7001 ~ 7999 | 活动报名 7001 起 |
| activity_checkin | 8001 ~ 8999 | 签到 8001 起 |
| post | 9001 ~ 9999 | 动态 9001 起 |
| comment | 10001 ~ 10999 | 评论 10001 起 |
| user_like | 11001 ~ 11999 | 点赞 11001 起 |
| fund | 12001 ~ 12099 | 经费申请 12001 起 |
| fund_record | 13001 ~ 13999 | 流水 13001 起 |
| notice | 14001 ~ 14099 | 公告 14001 起 |
| sys_role/sys_menu/dict_* | 不动种子，仅在需要时补充（沿用 1~99 小段） | — |
| sys_oper_log / sys_login_log | 15001 起 / 16001 起 | 日志数据 |

## 2. 逐表编写规范

> 未提及的字段 = 按 DDL 默认值即可。每表给「必填/关键规则/合格示例」。

### 2.1 sys_user（用户，种子已有 admin id=1）
- 必填：`username`（唯一，建议 `stu1001`~`stu1015`、`pres1001` 风格）、`nickname`（中文名，真实感）、`password`（固定 hash）、`user_type`（`STUDENT`）、`status='0'`。
- 建议 15~25 条：学生 12~18 名、社长 3~5 名（`user_type` 仍为 `STUDENT`，社长身份由 `club_member.member_role` 表达）。
- 合格示例：
  ```sql
  INSERT INTO sys_user (id, username, password, nickname, email, phone, user_type, status, create_time, update_time, deleted)
  VALUES (1001, 'stu1001', '$2a$10$7JB720yubVSZvUI0rEqK/.VqGOZTH.ulu33dHOiBE8ByOhJIrdAu2',
          '林晓雨', 'linxy@example.com', '13800001001', 'STUDENT', '0', '2026-06-01 09:00:00', '2026-06-01 09:00:00', 0);
  ```

### 2.2 club（社团）
- 必填：`name`（唯一，真实社团名）、`code`（唯一，`CLUB2001` 式编号）、`category`（四类之一）、`description`、`status`、`create_user_id`（指向 sys_user）、`president_id`（指向社长用户）、`member_count`（=ACTIVE 成员数）、`star_level`(0~5)。
- 时间：`apply_time < audit_time`；`REJECTED` 社团的 `audit_remark` 必填理由。
- 建议 8~12 条，状态分布：APPROVED 6~8、PENDING 1~2、SUSPENDED 1、REJECTED 1、DISSOLVED 1（终态社团无任何子数据）。
- 合格示例：
  ```sql
  INSERT INTO club (id, name, code, description, category, president_id, status, member_count, star_level,
                    create_user_id, apply_time, audit_time, audit_user_id, create_time, update_time, deleted)
  VALUES (2001, '晨光摄影社', 'CLUB2001', '用镜头记录校园四季，每周外拍交流。', 'CULTURE', 1016, 'APPROVED', 3, 4,
          1016, '2026-05-10 10:00:00', '2026-05-12 14:00:00', 1, '2026-05-10 10:00:00', '2026-05-12 14:00:00', 0);
  ```

### 2.3 club_member（社团成员）
- 必填：`club_id`+`user_id`（联合唯一）、`member_role`、`status`、`join_time`。
- 铁律：每个 APPROVED 社团恰好 1 个 `PRESIDENT`；`president_id` 与社团表一致；`member_count` 与 ACTIVE 数一致。
- 入社流程感：`PENDING` 成员有 `apply_time` 无 `join_time`；`ACTIVE` 成员 `apply_time < join_time`；`QUIT/REMOVED` 有 join_time。
- 合格示例：
  ```sql
  INSERT INTO club_member (id, club_id, user_id, member_role, status, apply_time, join_time, audit_user_id, create_time, update_time, deleted)
  VALUES (3001, 2001, 1016, 'PRESIDENT', 'ACTIVE', '2026-05-10 10:05:00', '2026-05-12 14:30:00', 1, '2026-05-10 10:05:00', '2026-05-12 14:30:00', 0);
  ```

### 2.4 recruit（纳新）+ 2.5 recruit_record（报名记录）
- recruit 必填：`club_id`、`title`、`quota`(>0)、`applied_count`、`start_time < end_time`、`status`、`requirements`。
- 状态与时间联动：`NOT_STARTED`（now 前于窗口）、`IN_PROGRESS`（窗口内）、`ENDED`（窗口已过且 `applied_count` 有值）、`CANCELLED`（随时）。
- recruit_record 必填：`recruit_id`+`user_id`（唯一）、`status`、`apply_time`（在窗口内）。
- 录取流转：`PASSED` 记录应有 `interview_time` + `interview_result` 评语；同一条 recruit 的 `PENDING+PASSED` 数量 == recruit.applied_count。
- **同一用户对同一 recruit 只能有一条记录**（唯一约束）。

### 2.6 activity（活动）+ 2.7 activity_signup + 2.8 activity_checkin
- activity 必填：`club_id`、`title`、`content`、`start_time < end_time`、`quota`、`applied_count`、`status`、`checkin_enabled`。
- 状态机时间联动：`DRAFT/PENDING` 窗口在未来；`PUBLISHED` 窗口临近；`ONGOING` 窗口内；`ENDED` 窗口已过。
- activity_signup：`SIGNED` 数 == activity.applied_count；`signup_time` 在窗口内。
- activity_checkin：**只给 `checkin_enabled='Y'` 且 `ONGOING` 的活动**编签到；签到者必须先有 `SIGNED` 报名记录；`checkin_time` 在窗口内；同活动同用户仅一条（唯一约束）。

### 2.9 notice（公告）
- 必填：`club_id`（`0` = 平台级，其余指向 club）、`title`、`content`、`publish_user_id`、`publish_time`、`status='0'`、`top`（`Y` 至多 2~3 条）。
- 平台公告 `publish_user_id` 指向管理员(1)；社团公告指向社长。

### 2.10 post（动态）
- 必填：`club_id`（指向 APPROVED 社团）、`author_id`（该社团 ACTIVE 成员）、`content`（真实感内容，别写"测试动态1"）、`like_count`/`comment_count`（与明细一致）。
- `club_id` 为 NULL 表示个人动态（可少量）。

### 2.11 comment（评论）
- 必填：`biz_type`（POST/NOTICE/ACTIVITY）、`biz_id`（指向已存在的对应业务 ID）、`user_id`、`content`。
- 评论的时间要晚于被评论对象的时间。
- `post.comment_count` 必须等于该 post 的 comment 记录数。

### 2.12 user_like（点赞）
- 必填：`biz_type`（`POST` 或 `COMMENT`，与代码取值一致）+`biz_id`+`user_id`（联合唯一）、`status='1'`。
- `biz_type='POST'` 时 `biz_id` 指向 post.id，计入 `post.like_count`；`biz_type='COMMENT'` 时指向 comment.id，计入 `comment.like_count`。
- 一个人对同一对象只能点一次赞（唯一约束）。

### 2.13 fund（经费申请）+ 2.14 fund_record（流水）
- fund 必填：`club_id`、`title`、`amount`（**>0**，CHECK 约束）、`type`、`status`、`apply_user_id`（社团成员）。
- fund_record：只给 `APPROVED` 的 fund 编流水；`balance_after` 按社团逐笔累加（见铁律 5）；`fund_id` 指向来源申请。
- 故事化建议：某社团 3 笔流水 = 迎新经费收入 2000 → 器材支出 1200 → 讲座支出 500 → 余额 300，逐笔 balance_after 为 2000/800/300。

### 2.15 sys_oper_log / sys_login_log（日志）
- sys_login_log：`user_name`、`ipaddr`（如 `10.1.2.3`）、`status`（`0`成功/`1`失败）、`msg`、`login_time`。
- sys_oper_log：`title`、`business_type`（1增/2改/3删/0其它）、`oper_name`、`oper_url`、`request_method`、`oper_ip`、`status`(0/1)、`oper_time`。
- 日志数据量可以大（30~60 条），时间均匀分布。

### 2.16 种子表不重复编写
`sys_menu`(16 条)、`sys_role`(3 条)、`sys_role_menu`、`dict_type`(4 条)、`dict_data`(16 条)、`sys_config`(3 条)、`sys_user(id=1 admin)`、`sys_user_role(1,1)` 已由 Flyway 种子提供，**不要重复 INSERT**；只需为新增用户补 `sys_user_role`（学生配 role_id=3、社长额外配 role_id=2）。

## 4. 交付格式规范

1. **文件**：`backend/src/main/resources/db/testdata/R__demo_data.sql`（Repeatable 迁移，Flyway 每次 checksum 变化时重新执行）或独立脚本 `backend/src/main/resources/db/testdata/demo_data.sql`——二选一，由执行方决定，命名统一。
2. **文件头**：注明"演示测试数据 / 生成日期 / 对应规范版本 / 账号密码统一 admin123"。
3. **顺序**：严格按第 2 节表序（先父后子），每表数据用分节注释隔开。
4. **格式**：每条 INSERT 独立语句、显式列出全部有值列名（便于审阅）、ID 用分段值、时间用固定字面量。
5. **幂等性**：脚本可重复执行（前置 `DELETE` 或使用固定 ID + `ON DUPLICATE` 思路由执行方选择并说明）。

## 5. 验收标准（数据合格 = 全部满足）

- [ ] SQL 在空库 Flyway 迁移完成后可一次执行成功，零报错（唯一约束/CHECK/类型）
- [ ] 应用启动后 `admin/admin123` 与新增测试账号（如 `stu1001/admin123`）均可登录
- [ ] 抽查 3 个社团：`member_count` 与 ACTIVE 成员数一致、社长恰好 1 人且 `president_id` 正确
- [ ] 抽查 2 个纳新/活动：`applied_count <= quota` 且与明细一致
- [ ] 抽查 1 个社团经费：`fund_record.balance_after` 逐笔累加正确
- [ ] 抽查 3 条动态：`like_count`/`comment_count` 与明细一致
- [ ] 无任何非法状态流转、无时间线穿越（结束早于开始等）
- [ ] 所有引用 ID 均真实存在

## 6. 不合格示例 vs 合格示例（对照）

| 场景 | ❌ 不合格 | ✅ 合格 |
|---|---|---|
| 状态 | `club.status='FINISHED'`（枚举不存在） | `club.status='DISSOLVED'` |
| 关联 | `club.president_id=9999`（用户不存在） | `club.president_id=1016`（真实社长） |
| 时间 | 活动 `start_time='2026-09-01', end_time='2026-08-01'` | `start < end` |
| 计数 | `member_count=5` 但只有 3 条 ACTIVE 成员 | 精确相等 |
| 状态机 | 给 `DISSOLVED` 社团的活动编 `ONGOING` | 终态社团无子数据 |
| 金额 | `fund.amount = -500`（CHECK 拒绝） | `fund.amount = 500` |
| 密码 | 自编 BCrypt 串（无法登录） | 统一固定 hash（明文 admin123） |
| 内容 | `post.content='测试动态1'` | `post.content='今天外拍去了江边，日落绝了，出片 200 张'` |
