# 社团生命周期设计

> 状态：**讨论记录（未实现）** —— 按阶段逐步完善，后续讨论逐段写入
> 定位：企业工程化视角的社团全流程设计（非毕设简化版）
> 约束：状态机驱动、审批链可审计、AI 只出建议人审生效、数据库约束兜底

---

## 0. 设计总原则

1. **状态机驱动**：社团全生命周期（申请 → 成立 → 运营 → 换届 → 解散/注销）显式建模，状态流转全程审计留痕
2. **门槛的语义是"质量过滤 + 审批依据沉淀"**：每层关卡产出的数据（联名清单、老师确认、规划材料）是审批依据与审计素材，而非单纯限制数量
3. **AI 权力边界**：AI 只"挡"不"放"——可拦截并说明理由，批准权永远在人（管理员/老师）
4. **锁必须有解锁路径**：所有资源占用（指导老师 1:1、名额）必须定义释放时机，防止生命周期后半段死锁
5. **数据库约束兜底**：唯一约束、外键写进 schema，不依赖业务代码单点保证

## 1. 身份模型（两层 RBAC）

### 1.1 设计核心：两层权限体系

**平台身份（sys_user.user_type + sys_role）——登录即拥有，全局**
**社团身份（club_member.member_role）——资源相关，随加入/退出/任职动态变化**

> 决策理由：社长/副社长/普通成员不是人固有的身份，而是"某人在某社团里的角色"。
> 若平铺进全局 sys_role：加入 5 个社团产生 5 条角色记录、退社频繁增删、且无法回答
> "他在哪个社团有管理权限"。分层后：加入/退出/换届只改 club_member 一行；
> 权限判定 = 平台身份权限 ∩（针对社团资源时的）社团身份权限。
> 两层并存不互斥：一个人可以同时是 student（平台）+ MEMBER（社团）。

### 1.2 平台层角色

| 角色 | 定位 | 数据范围 | 备注 |
|---|---|---|---|
| student 学生 | 基础用户：浏览内容广场/报名/申请/联名/发帖 | 本人（data_scope=4） | 入社后平台身份不变，社团身份叠加 |
| teacher 指导老师 | 社团内部角色：1:1 挂靠；知情确认、可参加社团活动、线下查阅活动情况；能力仅限社团范围内 | 挂靠社团（club_advisor 关联） | 归属学院**不重要**（不参与归属判定）；参照"老师牵头社团"真实形态，非行政审批者 |
| approver 校方审批员 | 校方"优良安全的管理"执行者：内容广场浏览/审批（成立终审、经费、上诉）/活动日历视图（时间×地点×规模）/举报处理 | **院级实例 = 本院社团**（新增 data_scope 档位：按学院归属）/ **校级实例 = 全校** | 两级=同一角色×数据范围差异，非两个角色；账号按"每院一实例"设计，校级全局 |
| admin 系统管理员 | 只管系统配置（用户/角色/菜单/字典/参数） | 全部（data_scope=1） | 业务审批职责已拆出（归 approver），不再当"业务法官" |
| tech_admin 技术管理员 | 只管运行监控（监控中心/日志/指标） | 运行数据，不碰业务数据 | 已实现 |

### 1.3 社团层角色（club_member.member_role）

| 角色 | 定位 | 备注 |
|---|---|---|
| PRESIDENT 社长 | 社团全权运营（成员/活动/纳新/经费/换届） | 成立时发起人自动担任；权限子集待逐步细化 |
| VICE_PRESIDENT 副社长 | 新增概念：社长权限子集（具体范围待讨论） | 默认建议：可成员审核/活动发布/纳新/经费申请；不可换届/解散/移除社长；数量 1-2 可配置 |
| MEMBER 普通成员 | 参与活动/查看社团内部内容 | 入社即得 |

### 1.4 关键约束

1. **一学生可加入多个社团**：club_member 允许多条 MEMBER 记录（不同 club_id）
2. **一学生至多管理一个社团（在职唯一，已确认）**：管理身份（PRESIDENT 或 VICE_PRESIDENT）全局至多一个 ACTIVE
   - 数据库实现：条件唯一索引（H2/MySQL 兼容写法）
     ```sql
     CREATE UNIQUE INDEX uk_member_manager ON club_member(user_id)
     WHERE member_role IN ('PRESIDENT', 'VICE_PRESIDENT') AND status = 'ACTIVE';
     ```
   - 语义：历史当过社长不占位；退出/撤职/换届后自动释放（锁的解锁路径）
   - 推论：社长可以普通成员身份加入其他社团（不拦），但申请成为第二个社团的管理者时被拒

### 1.5 归属责任制（校级/院级）

- 社团归属 = **社长所在学院**（责任唯一：安全事宜全权归该院）
- **换届归属迁移**：随社长迁移，校级**只收通知、不审批**（归属变更 = 通知事件，非审批事件）
- 指导老师学院不参与归属判定（仅数据展示）
- 跨院成员不参与管辖（责任唯一化的刻意取舍）

### 1.6 举报分流（倾向方案，待细化）

```
学生举报 → 系统自动分流
  ├─ 轻微违规（辱骂/引战）→ 院级处理（警告/删帖，本院社团内容）
  └─ 严重违规（涉政/诈骗/色情）→ 校级直接处理（封禁账号/社团）
```

### 1.7 开放项（权限随讨论逐步长出）

- approver 审批清单逐项确认（哪些动作进审批、哪些进通知）
- 副社长权限子集
- admin 拆分后现有审批接口的迁移方案
- 指导老师更多权限细节（能看不能批：批是社长/校方的事）
- 活动日历的场地冲突检测（二期演进项）

## 2. 阶段一：社团申请与审批

### 2.1 流程总览（状态机草案）

```
DRAFT       发起人填主表单，生成分享链接
  ↓ 分享链接 + 联名人登录填写（严苛校验）
COLLECTING  联名收集期（时限 N 天，超时 EXPIRED）
  ↓ 联名人数 ≥ 阈值
TEACHER     指导老师确认（老师账号填写确认声明，1:1 锁定）
  ↓ 老师确认 + 联名人数达标
SUBMITTED   提交系统查验
  ↓ ① 自动校验（材料完整性、人数、老师、唯一性）
  ↓ ② AI 查重（向量相似度 Top-N + LLM 判定 + 证据引用）
  ├─ 不重复 → 人工终审（管理员看全套材料）→ APPROVED / REJECTED
  └─ 疑似重复 → AI 拒绝 + 理由 + 相似社团信息（站内联系入口）
        ↓ 发起人 + 指导老师 双签名上诉（N 天窗口）
        ├─ 不上诉 → REJECTED（失败案例入库）
        └─ 上诉 → 管理员人工终审
              ├─ 通过 → APPROVED
              └─ 驳回 → REJECTED（理由结构化入库，供后续 agent 参考）

旁路：COLLECTING / TEACHER 超时 → EXPIRED；发起人放弃 → CANCELLED
```

### 2.2 表单设计（严苛填写）

**主表单（发起人）**：名称、类别、宗旨、**年度活动规划**（最小字数限制）、**活动安全预案说明**、承诺条款勾选。

**联名表单（联名人，通过分享链接）**：
- 登录后填写（链接只是入口凭证，不是免登录通道）
- 结构化必填 + 校验（学号格式、最小字数、模板化问答）
- 末尾独立**承诺确认步骤**："我确认：如实填写，通过后加入社团"
  - 设计要点：**联名人"填写"（意向）与"承诺"（最终确认）分开记录**——成立批量落位时只有承诺者入册，避免"填了表不认账"

### 2.3 AI 查重设计（核心 AI 落地）

- **技术底座**：复用现有 bge embedding + 向量库（SimpleVectorStore）——新申请文本 vs 已有社团简介的向量相似度 Top-N 检索
- **判定链**：向量检索 Top-N → LLM 依据检索证据判定 → 结构化输出
- **输出约束（防幻觉）**：拒绝理由 = 结构化 JSON（判定 + 相似度分数 + 引用的相似社团 + 相似片段摘录），**LLM 只能引用检索到的证据**；检索不到相似片段 → 不允许判"重复"（fail-closed）
- **拒绝时的相似社团信息**：不直接提供社长手机号/微信（隐私），改为**站内联系入口**（发起人站内信 → 社长回复）——为「消息通知」模块提供真实用例
- **失败案例库**：管理员驳回时选择**结构化原因分类**（内容重复 / 材料不实 / 安全风险 / 不符合宗旨）；后续 AI 查重时，将同类历史失败案例作为检索结果之外的**额外上下文注入判定 prompt**（"历史有 3 个类似申请被驳回，理由：……"）——工程上最稳的"AI 从历史学习"，无需训练、效果可解释

### 2.4 防滥用机制

| 关卡 | 设计 |
|---|---|
| 资料门槛 | 结构化必填 + 长度下限 + 模板化（过滤"一时兴起"） |
| 联名门槛 | 人数 ≥ 3（可配置）、`(application_id, user_id)` 唯一约束防刷票、联名人不得是发起人本人、投票明细留痕 |
| 老师门槛 | 1:1 锁定 + 老师确认记录（时间戳 + 身份 + 知情声明） |
| 冷却与限额 | 同用户进行中申请唯一、驳回后 N 天内不得重提同名/同类、单用户年度发起上限（可配置） |

**配额语义（与门槛区分）**：门槛过滤"不合格"，配额治理"数量"（全校活跃社团上限/类别配额）——两者是不同机制。

### 2.5 指导老师确认时序

- 发起人在申请时指定**老师候选**（候选池 = 已导入的未绑定老师）
- 投票/联名达标后才进入 TEACHER_CONFIRM——老师只被"有资格"的申请打扰
- 老师确认页展示：社团资料 + 联名人清单 + 活动规划 → 勾选知情同意 → 生成确认记录
- **1:1 数据库约束**：`club_advisor.teacher_user_id` 唯一 + `club_id` 唯一
- **释放路径**：管理员驳回后老师 1:1 锁**自动释放**（可被其他申请邀请）；社团解散/注销时释放
- 老师拒绝挂靠后：允许发起人**换老师重新确认**（待决策）

### 2.6 成立瞬间批量落位（APPROVED 事务）

审批通过 = 单事务批量初始化，失败全回滚：
- 发起人 → club_member（PRESIDENT, ACTIVE）
- 承诺联名人 → club_member（MEMBER, ACTIVE）
- 指导老师 → club_advisor（绑定）
- 社团 APPROVED + 默认运营参数

### 2.7 待决策项（未定）

1. 联名人"填写即承诺" vs "填写 + 独立承诺两步"（推荐两步，已写入 2.2）
2. AI 查重时机：提交后自动跑（推荐）vs 管理员手动触发
3. 上诉窗口天数（建议 3–7 天可配置）
4. 老师拒绝后：换老师重走确认（推荐）vs 申请失效
5. 驳回后重提：修订重提（保留记录）vs 全部重来
6. 相似社团信息提供方式：站内联系入口（推荐，隐私合规）vs 直接给联系方式

### 2.8 存量数据迁移（上线时）

存量种子社团（无老师、无联名记录）处理：限期补录指导老师，否则冻结——具体方案待定，文档占位。
