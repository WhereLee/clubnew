# 技术管理员设计（Tech Admin）

> 状态：**设计文档（未实现）** —— 功能留待后期落地，可能部分或全部排在最后
> 定位：本项目作为企业级开发敲门砖的"运维 / 观测 / AI 治理"能力面
> 对标：LangSmith / LangFuse / LangGraph Studio 的简化自研形态

---

## 1. 背景与目标

### 1.1 为什么需要技术管理员

原项目只有三种角色（student / president / admin），技术运维职责由系统管理员（admin）兼任。
在"毕设规模"视角下这是合理简化，但在"企业敲门砖"视角下不成立：

- 企业中**性能治理**（速度 / 安全 / 质量）是主流关切，业务代码可以不完美，但运行的可观测性、
  稳定性治理是基本盘；
- 应届生简历最不会讲、企业最缺的能力恰好是**运维 / 观测 / AI 治理**；
- AI 链路（prompt、工具调用、token 消耗）在 2026 年已进入企业治理范畴，需要独立于业务管理的
  控制台。

### 1.2 目标

1. **角色分离**：业务管理员（admin 管人、管业务审批）与技术管理员（tech_admin 管系统运行与 AI 链路）边界清晰——对应企业 DBA / SRE / 算法平台团队与业务系统的分离，本身就是面试故事。
2. **Agent 全链路可观测**：结构可见（图状拓扑）、运行可见（trace 时间线）、配置可控（prompt 版本化）。
3. **性能治理可视化**：速度（延迟）、安全（攻击面趋势）、质量（数据/工具成功率）收拢到一个控制台。

## 2. 角色定义与权限边界

| 维度 | 系统管理员 admin | 技术管理员 tech_admin |
|---|---|---|
| 管什么 | 人（用户/角色/菜单/字典/参数）、业务审批（社团/经费） | **系统运行**（监控/日志/指标）+ **AI 链路**（agent 观测/prompt 治理） |
| 数据权限 | data_scope=1，全部业务数据 | **不看业务数据**，只看运行数据（日志/指标/轨迹/统计） |
| 典型动作 | 审批社团、重置密码 | 看今日 P95、查一次失败的工具调用链、审阅 prompt 新版本 |
| 关键约束 | —— | **不可修改业务数据**；prompt 改动必须人审生效（与项目"AI 只出建议、人审生效"铁律一致） |

设计要点：

- `tech_admin` 复用现有 RBAC 体系（sys_role 加角色 + sys_menu 加菜单 + data_scope 语义）
- 权限控制到接口：tech_admin 只开放 `/monitor/**`、`/agent/admin/**`、`/system/log/**` 域
- 技术管理员与系统管理员**互斥不互兼**（企业实践：职责分离，避免一人身兼审计与被审计）

## 3. 四层能力设计

### L1 拓扑可视化（Agent 结构图）

**目标**：运维人员不用翻代码就能看到"项目里有哪些 agent、各自挂了哪些工具、权限域是什么、未来子代理挂在谁下面"。

**现状**：项目为单层 agent + 工具注册表（`AgentToolRegistry`），无子代理。

**设计**：

- 新增 `agent_definition` 元数据表：`agent_key`、名称、描述、模型、prompt 版本引用、工具清单、
  权限域、`parent_key`（父代理，预留子代理）、状态
- 前端用图组件（AntV X6 或 vue-flow）渲染节点图：`技术助手 → TodayErrorTool / DataHealthTool / SystemHealthTool`、`业务助手 → SqlQueryTool / ApprovalAssistTool`、`用户助手 → KnowledgeSearchTool`
- 未来加子代理（参考 LangGraph 的图状编排）时，`parent_key` 让图自动多一层，前端零改造

**诚实评估**：核心价值在"配置可视化"；工作量主要在前端图组件。

### L2 运行时链路追踪（Trace）

**目标**：把一次问答展开成可回放的时间线——这是 LangSmith 的核心形态，也是面试杀伤力最大的能力。

**现状**：已有 `agent_tool_log`（工具名 / 参数 / 结果 / 耗时 / 成功），但缺**一条消息的完整调用链**。

**设计**：

- 每次对话生成 `traceId`（会话级或消息级），贯穿：`用户输入 → LLM(2.1s) → 工具调用(180ms) → LLM(1.2s) → 回答`
- 前端时间线视图：每个节点可点开看输入输出、耗时、token 消耗
- 数据落点：`agent_tool_log` 补 `trace_id` 列；`agent_message` 补 token 统计列
- **待决策**：深度做到"单次对话完整链路"（推荐，改动可控），还是"全局检索任意 trace"（LangSmith 式检索，工作量大）

### L3 Prompt 治理（版本化 + 可视化）

**目标**：解决"prompt 硬编码在代码里无法控制"的长期痛点（用户核心诉求）。

**设计**：

- 新增 `agent_prompt` 表：`agent_key`、`version`、`content`（system prompt）、`tool_descriptions`（工具描述 JSON）、`created_by`、`status`（DRAFT/ACTIVE/ARCHIVED）
- 运行时 `AgentServiceImpl` 从 DB 加载 ACTIVE 版本（首次实现时同步现有硬编码 prompt 为 v1）
- 技术管理员端：查看全部 agent 的当前 prompt、历史版本、**版本 diff 对比**、回滚、新建草稿
- **待决策**：版本化范围是否包含工具描述（tool description 也是 prompt 的一部分，直接影响模型选工具，工具调用失败率高往往根因在此）——建议包含

### L4 质量分析与优化建议

**目标**：数据驱动的 prompt 优化闭环，且遵守项目安全铁律（机器统计 → LLM 起草 → 人审 → 生效）。

**设计**：

- `@Scheduled` 定时任务聚合 `agent_tool_log` / `agent_message`：
  - 各工具调用次数 / 失败率 / 平均耗时 / 拒绝率
  - token 消耗趋势（按 agent / 按天）
  - 用户提问分布（高频问题 → 知识库缺口提示）
- 建议生成：LLM 读取统计 + 当前 prompt，起草优化建议（如："SqlQueryTool 本周拒绝率 34%，建议在 system prompt 补充 XX 表述"）
- **闭环**：建议 → 技术管理员人审 → 生成新 prompt 版本（DRAFT→ACTIVE）→ A/B 观察指标
- **冷水（预期管理）**：企业真实实践是"观测 + 评估集 + 人审"，让 LLM 自改自生效的产品极少——prompt 改坏是无声的（质量下降无报错）。所以**自动化上限 = 起草建议，永远人审生效**。这一致性与项目安全铁律天然同构，是完整的故事。

## 4. 性能治理仪表盘（速度 + 安全 + 质量）

| 维度 | 指标 | 数据源（现有） |
|---|---|---|
| 速度 | 接口 P95 延迟、今日最慢接口 Top10、agent LLM/工具耗时分布 | Prometheus（已有 HTTP 指标）+ agent_tool_log |
| 安全 | 登录失败趋势、越权尝试、AI 工具拒绝率（NL2SQL 拦截率） | sys_login_log + agent_tool_log |
| 质量 | 数据体检报告（社长缺失/计数不一致/孤儿引用）、agent 工具成功率 | DataHealthTool + agent_tool_log |

前端形态：`/monitor/overview` 概览页（三块指标卡片 + 趋势图），Grafana 保留给更细粒度。

## 5. 数据模型变更草案

```sql
-- 角色（现有 sys_role 增行）
-- role_key = 'tech_admin', data_scope = '1'（运行数据全量，但无业务数据接口权限）

-- 菜单（现有 sys_menu 增行）
-- /monitor/overview、/monitor/agent、/monitor/prompt、/monitor/trace

-- agent_definition：agent 元数据（含父级，预留子代理）
CREATE TABLE agent_definition (
    id BIGINT PRIMARY KEY,
    agent_key VARCHAR(64) NOT NULL UNIQUE,
    name VARCHAR(128), description VARCHAR(512),
    model VARCHAR(64), prompt_version INT,
    tools_json TEXT, access VARCHAR(16),
    parent_key VARCHAR(64),      -- 子代理预留
    status VARCHAR(16),
    create_time DATETIME, update_time DATETIME, deleted TINYINT
);

-- agent_prompt：prompt 版本化
CREATE TABLE agent_prompt (
    id BIGINT PRIMARY KEY,
    agent_key VARCHAR(64) NOT NULL,
    version INT NOT NULL,
    content TEXT,                -- system prompt
    tool_descriptions TEXT,      -- 工具描述 JSON（待决策：是否纳入版本化）
    created_by BIGINT, status VARCHAR(16),  -- DRAFT / ACTIVE / ARCHIVED
    remark VARCHAR(255),
    create_time DATETIME, update_time DATETIME, deleted TINYINT
);

-- 既有表补列

-- agent_message  ADD prompt_tokens / completion_tokens
```

## 6. 落地路线（P0–P4，全部留待后期，可部分执行）

| 阶段 | 内容 | 工作量评估 | 依赖 |
|---|---|---|---|
| P0 | tech_admin 角色 + 权限体系（RBAC + 接口域） | 小 | 无 |
| P1 | 观测底座：traceId + agent 运行统计（复用现有表补列） | 小-中 | 无 |
| P2 | Prompt 治理：DB 版本化 + 查看/回滚/对比 | 中（侵入式，AgentServiceImpl 改读 DB） | P0 |
| P3 | 前端：图状拓扑 + trace 时间线 + prompt 管理页 | 中-大（图组件） | P1/P2 |
| P4 | 建议闭环：定时分析 + LLM 起草 + 人审生效 | 中 | P2 + 真实模型可用 |

**推荐执行时机**：放在三端 agent 真实模型联调验证之后；若时间紧，P0+P1 优先
（观测底座是后续一切的上游，且不改动业务逻辑，风险低）。

## 7. 待决策项（需用户拍板）

1. **trace 深度**：单次对话完整链路时间线（推荐）vs 全局检索任意 trace（LangSmith 式）
2. **prompt 版本化范围**：仅 system prompt vs 含工具描述（推荐含，工具描述是工具调用失败率高发的根因层）
3. **自动优化的自动化程度**：LLM 起草 + 人审生效（推荐，与安全铁律一致）vs 更高自动化（自动生成版本默认不生效）

## 8. 面试价值

- **对标行业**：自研简化版 LangSmith / LangFuse / LangGraph Studio——"我没有用现成平台，而是理解其核心
  （trace / prompt 版本化 / 评估闭环）后在单体项目里落地"
- **职责分离**：业务管理员与技术管理员分离 = SRE/DBA 与业务系统边界的企业实践
- **性能治理**：速度（P95）+ 安全（登录失败/拒绝率）+ 质量（数据体检）三合一控制台
- **AI 治理成熟度**：prompt 当配置管理（版本化/回滚/人审），是 2026 年企业 AI 工程的共识
